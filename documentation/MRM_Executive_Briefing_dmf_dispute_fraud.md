# Debit-Card Dispute Fraud Model (`dmf` v0.2.0) — Pre-Submission Validation Briefing for Model Risk Management

**Prepared:** 6 September 2026 · **Scope:** `dmf/` package on branch `dmf_v2`, shipped configuration `configs/dispute_fraud.yaml`, shipped artifact `artifacts/dispute_fraud_v1/`, and the research walkthrough under `examples/`. Every quantitative claim below was re-derived by executing the code in this repository; nothing is taken from documentation or notebook output alone.

---

## 1. Model / Framework Overview

The `dmf` package is a scikit-learn-based framework for building a binary classifier that scores an incoming debit-card dispute for the probability that it is a **first-party fraudulent dispute**. The output is intended to drive an operational routing decision: at a configured review budget (top 5% of volume by score, `configs/dispute_fraud.yaml:189-192`) a dispute is flagged for investigator review; everything else proceeds on the standard path. A production wrapper (`src/dmf/inference.py`) additionally routes any record whose inputs fall outside the training support to manual review, so the decision is human-in-the-loop for flagged and out-of-support cases and autonomous for the remainder.

Two prediction-generating components exist. The **production core** is a fitted scikit-learn pipeline: column typing, winsorisation, median imputation with missing indicators, standard scaling, rare-level collapsing, a categorical encoder (one-hot, ordinal, weight-of-evidence or cross-fitted target encoding), an inference guard, and an estimator. The **research harness** (`src/dmf/research/`) searches an estimator zoo (two L2 logistic regressions, XGBoost, LightGBM, `configs/dispute_fraud.yaml:229-323`) over nested variable subsets ranked by model-native importance, applies a one-standard-error parsimony rule, confirms on a stratified holdout, derives a decision threshold from holdout scores, and refits the winner on all data for shipment. Architecturally this is a traditional-ML pipeline; no GenAI component executes anywhere in the codebase. A phase-2 Cortex-based narrative-explanation layer is described in `snowflake_cortex_updates.md` but has not been built.

Two facts frame everything that follows. First, **all evidence in the repository is on synthetic data** (`examples/generate_synthetic_disputes.py`) generated from a known latent logistic model; the pipeline has never been fitted to bank data, and the synthetic panel carries **no timestamp and no customer identifier**. Second, the shipped artifact in `artifacts/dispute_fraud_v1/` (23 Aug 2026) **predates several code fixes** and is no longer what the current code produces (Section 3, Finding 1).

## 2. Validation Criteria Identified

**Governance tiering.** The scoring pipeline (feature transformer plus estimator) meets the model definition under SR 11-7 / OCC 2011-12 and receives the full three-pillar treatment: conceptual soundness, outcomes analysis, and ongoing monitoring. The preprocessing steps that learn parameters from data (winsoriser bounds, imputation medians, WOE tables, rare-level vocabularies, guard envelopes) and the threshold-derivation rule are treated as components of that model and are validated inside it rather than separately. The synthetic-data generator is a test fixture, not a model. The research harness is development tooling; it is not deployed, but because it *chooses* the specification that ships, its selection logic is in scope for conceptual soundness. No GenAI component is present, so no SR 26-2-style threshold test applies today; the repository contains no internal MRM framework document, so terminology here defaults to SR 11-7, and MRM should confirm which internal standard governs. When the planned explanation layer is built it will consume scores rather than produce features or labels, which likely places it below the model-definition threshold and under lightweight observability governance (golden-path holdout tests re-run on prompt or model change, groundedness scoring); that determination is deferred until it exists.

**Quantitative criteria selected.** For a low-prevalence ranking model whose output drives a capacity-constrained review queue, the criteria applied were: (i) temporal validity and absence of leakage in the executing code path, tested by code trace and by a shuffled-label probe; (ii) validation design that separates selection from confirmation, and whether the reported estimate describes the specification that ships; (iii) discrimination on the holdout — average precision as primary given ~7.5% prevalence, with ROC-AUC, KS, recall at 1% false-positive rate and lift at the 5% review budget — each recomputed from stored predictions with bootstrap intervals; (iv) calibration (Brier score against the constant-prevalence baseline, expected calibration error, decile reliability), because the wrapper emits a column literally named `fraud_probability` (`src/dmf/inference.py:134`); (v) overfitting, via train-minus-validation gap and CV-to-holdout decay; (vi) benchmarking against a simpler challenger and a single-variable baseline; (vii) segment parity of flag rates on attributes the model is barred from using; (viii) reproducibility, environment pinning, and monitoring readiness.

## 3. Validation Results

**Confirmed strengths first, briefly.** The leakage discipline in the core is sound and was verified, not assumed. Every learned statistic — including the supervised WOE and target encoders — lives inside a scikit-learn `Pipeline` that is refit within each CV fold (`src/dmf/pipeline.py:230-296`; `src/dmf/transformers.py:463-497`); `fit_transform` correctly returns the cross-fitted matrix (`src/dmf/pipeline.py:286-296`); and variable ranking is re-estimated inside every fold (`src/dmf/research/selection.py:540-551`). A shuffled-label run of the shipped configuration produced cross-validated AP of 0.072–0.084 against a prevalence of 0.075 and ROC-AUC of 0.48–0.52, i.e. no leakage signature. The 140-test suite passes in the current environment. Leaderboard and holdout numbers reproduce exactly from the row-level prediction store. Seeds are set and the holdout split reconstructs bit-for-bit from `train_test_split(random_state=42, stratify=y)` (718 / 179 positives in train / holdout, matching `run_report.json`).

**Finding 1 (invalidates the shipped artifact as evidence) — the artifact is not reproducible from the current code and was built with the imbalance policy and seed silently dropped.** Loading `artifacts/dispute_fraud_v1/model.joblib` shows the XGBoost step with `scale_pos_weight=None, random_state=None`, although the config declares `imbalance: scale_pos_weight` (`configs/dispute_fraud.yaml:300`). The defect in `zoo._accepts` has since been fixed (`src/dmf/research/zoo.py:40-61`). Re-running the identical configuration with today's code selects a **different champion**: logistic regression with WOE encoding on five variables (CV AP 0.337, holdout AP 0.351) instead of XGBoost on four variables (CV AP 0.325, holdout AP 0.240). The bundle's `dmf_version` check (`src/dmf/inference.py:259-272`) cannot detect this because the version string was never bumped. The artifact was also pickled under scikit-learn 1.9.0 / XGBoost 3.4.1 / Python 3.12 and loads into the current 1.8.0 / 3.2.0 / 3.14 environment only with `InconsistentVersionWarning` and an XGBoost serialization warning; `pyproject.toml:9-21` pins only lower bounds. *Confirmed.*

**Finding 2 (invalidates the reported estimate for the shipped specification) — the leaderboard's CV number describes the selection *procedure*, not the variable list that ships, and the champion's CV-to-holdout decay is outside its own error band.** Each leaderboard row pairs the top-k list from the full-training ordering with the score of a nested procedure whose per-fold lists differ (`src/dmf/research/selection.py:553-562`). For the shipped XGBoost k=4 spec the harness reported CV AP 0.325 ± 0.016; plain 5-fold CV of that *fixed* specification gives 0.293, and the holdout gives 0.240 (my refit reproduction 0.229, bootstrap 95% CI 0.172–0.292). The harness's own `within_one_se` flag reads `false` for this run. Three fresh synthetic samples of 12,000 disputes scored by the shipped bundle give AP 0.26–0.27, consistent with the holdout, not with the leaderboard. *Confirmed.*

**Finding 3 (invalidates the selection) — the one-SE rule treats variable count as the only complexity measure and chose a heavily overfit tree over a linear model that dominates it.** The rule selects the smallest k among *all* (model, k) cells within one SE of the best (`src/dmf/research/selection.py:750-759`). It picked a 250-tree XGBoost with train AP 0.49 versus CV 0.33 (`overfit_gap` 0.168 in `leaderboard.csv`) because k=4 is smaller than k=8, ignoring that the alternative was a logistic regression with an overfit gap of 0.008. On the holdout the passed-over logistic WOE k=8 specification scores AP 0.358 versus 0.229 for the shipped spec; a paired bootstrap of the difference gives +0.129 (95% CI 0.075–0.192). A single-variable baseline (`prior_disputes_12m` alone) scores AP 0.204 (CI 0.157–0.268), so the shipped four-variable tree model is statistically indistinguishable from one raw count. The chosen list also contains `cardholder_tenure_years` and `cardholder_tenure_months`, which are the same quantity (correlation 0.9998, VIF ≈ 2,837); the importance ordering is documented as ignoring redundancy (`src/dmf/research/ordering.py:15`). *Confirmed.*

**Finding 4 (invalidates temporal claims) — no out-of-time validation exists, and none is possible on the data at hand.** The shipped configuration uses `strategy: random` with `group_column` and `time_column` unset (`configs/dispute_fraud.yaml:165-167`), so the holdout is an i.i.d. stratified split (`src/dmf/research/selection.py:280-286`). The framework supports time and group-time splits and tests them, but the synthetic panel has no timestamp or customer key, so the shipped run cannot demonstrate forward-in-time performance, concept drift, or customer-level independence. On real data, disputes from one cardholder are not independent, and features such as `prior_disputes_12m`, `prior_dispute_upheld_ratio` and `internal_risk_score` must be point-in-time as of the dispute date; none of this can be verified here. *Open item pending real data.*

**Finding 5 (degrades reliability) — outputs are labelled probabilities but are not calibrated, and the class-imbalance policy makes them systematically wrong.** With `imbalance: balanced` / `scale_pos_weight` (`src/dmf/research/zoo.py:64-83`) the current champion predicts a mean of 0.384 against a prevalence of 0.075 (calibration ratio 5.2, ECE 0.31); its Brier score of 0.169 is **worse than predicting the base rate** (0.069). Decile reliability shows the top decile at mean score 0.83 versus observed rate 0.34. Calibration is deliberately left post-hoc (`README.md`, "Post-hoc steps"). Rank-based flagging is unaffected, but the `fraud_probability` column cannot be consumed as a probability by any downstream loss, expected-value or capacity model. Fitting isotonic regression on the out-of-fold CV scores and applying it to the holdout reduces Brier to 0.059 and ECE to 0.005, so the remedy is cheap and demonstrable. *Confirmed.*

**Finding 6 (degrades reliability) — the holdout is consumed before the shipped model exists.** The holdout sets the decision threshold (`src/dmf/research/selection.py:909`), then the winner is refit on train + holdout (`:935-937`) and the threshold re-derived from the refit model's *in-sample* scores on those same rows (`:997`). The shipped model therefore has no out-of-sample evidence of its own; the in-sample AP of the shipped bundle on the holdout rows is 0.360 versus 0.229 out-of-sample. On fresh synthetic samples the in-sample-derived cut yielded flag rates of 4.7–5.2% against a 5% target and PSI of 0.008–0.012, so in this stationary synthetic setting the consequence is small, but on real data with drift it is unbounded. *Confirmed mechanism; consequence open.*

**Finding 7 (hygiene) — inference and multiplicity.** Thirty-six paired Nadeau–Bengio t-tests run without correction (`src/dmf/research/selection.py:1224-1270`, summary at `:700`); one reaches p<0.05 and none survives Bonferroni (0.0014). The README correctly calls these decision aids, but the artifact reports "n_significant_improvements" without that caveat. Holdout metrics carry no confidence intervals (`src/dmf/metrics.py:331`); the bootstrap CI for the current champion's holdout AP is 0.276–0.428, which is the honest width any reader should see. The leaderboard's 40 cells are all scored on the same folds, so the top cell is subject to winner's-curse optimism that only the holdout can correct.

**Finding 8 (hygiene) — segment parity and monitoring.** On the current champion the flag rate at the 5% budget ranges from 2.6% (student segment) to 8.4% (affluent), a 3.2× disparity; the model uses none of these attributes directly, so the disparity is proxy-driven and needs a fair-treatment rationale before a Reg E routing use. PSI helpers, a training-envelope guard, and bundled reference quantiles exist and work (the drifted batch routed 118 of 2,000 records to manual review), but there is no scheduled drift job, no performance-decay tracking, no data-quality gate in a pipeline, and no recalibration or retrain trigger; the README explicitly defers these to "infrastructure". Sensitivity is acceptable: a ±5% perturbation of tenure changes the top-5% flagged set by 9%.

**Could not be evaluated:** real label definition, outcome window and label lag; investigation-dependent label truncation (disputes closed without investigation carry no label, the analogue of reject inference); customer-level clustering and effective sample size; label drift across policy changes; production scoring logs; and any GenAI component.

## 4. Recommended Remediation

**Must fix before MRM submission** (each invalidates the current performance evidence):

1. **Regenerate the artifact from the current code, on the intended data, and bump the version.** Delete `artifacts/dispute_fraud_v1/`, bump `dmf.__version__`, pin exact dependency versions in `pyproject.toml`, and rerun. Closure: `run_lineage` package versions match the deployment environment; loading the bundle emits no version warnings; the parity tests pass against the regenerated bundle.
2. **Report the CV estimate of the specification that ships.** After selection, score the fixed winning variable list with plain CV on the training partition and report that number beside the nested-procedure number; require agreement within one SE before the spec is eligible. Closure: for the shipped spec, fixed-spec CV, holdout, and a fresh out-of-time sample agree within the bootstrap interval.
3. **Repair the selection rule.** Apply the one-SE band within model family, or add an overfit-gap cap (e.g. reject cells whose train-minus-CV gap exceeds 3× the SE), and de-duplicate collinear candidates (VIF or correlation screen) before ordering. Closure: re-running the shipped config selects a spec whose overfit gap is below the cap and whose holdout AP is not statistically dominated by any simpler challenger in the zoo.
4. **Validate out-of-time and out-of-customer on real data.** Use `split.strategy: group_time` with the dispute open timestamp and customer key; verify every feature is point-in-time by joining feature snapshots as-of the dispute date, not current state. Closure: a holdout strictly later than training with CV-to-holdout decay inside the interval, and a group-leakage assertion of zero.
5. **Calibrate before shipping a probability.** Wrap the pipeline in `CalibratedClassifierCV` (isotonic, fit on out-of-fold scores) or rename the output `fraud_score` and document that it is rank-only. Closure: Brier below the constant-prevalence baseline and ECE below 0.02 on the out-of-time sample.

**Track as ongoing conditions:**

6. Keep a second untouched partition (or the out-of-time slice) that is never used for threshold derivation, so the shipped refit has its own out-of-sample confirmation; report `decision_flag_rate` on it, not on in-sample scores.
7. Add bootstrap intervals to `evaluate_predictions` and apply a Holm or Bonferroni adjustment to the marginal-gain table; remove the uncorrected "n_significant_improvements" headline.
8. Document the fair-treatment rationale for the observed flag-rate disparity, set a tolerance (e.g. no segment above 2× the population rate), and gate release on it.
9. Stand up scheduled monitoring: monthly PSI on scores and on each input, rolling AP / recall-at-budget once labels mature, guard-rate tracking, and a defined recalibration and retrain trigger. The building blocks already exist in `src/dmf/metrics.py` and `src/dmf/inference.py`.
10. Resolve the open data items in Section 3 (label definition, outcome window, label truncation, clustering) in the model development document before real-data fitting begins, and re-tier the explanation layer when it is built.
